# OctoSense 事务窗口：交互模型与研究依据

调研日期：2026-09-13

本文依据公开论文、作者说明及官方产品文档，评估以事务窗口组织 Agent 与用户交互的方向。没有试用所有产品，也没有进行 OctoSense 用户实验。文中的体验方案是设计建议；论文原型、产品能力和协议基础设施分别标明。

后续确认的产品要求已写入 [App Card 与事务 Tile 设计需求](app-card-design-requirements.md)，包括任意卡片的原始来源追溯、Email / Message Card 原位组合，以及旅行时间线、历史与未来卡片访问和出行 Sub Tiles。设计与实现验收以该需求文档为入口。

## 产品定义

OctoSense 的桌面可以围绕用户正在推进或长期照料的事情组织：你的冰箱、今年的体检、同学聚会、孩子的兴趣班、健身计划。

一个事务窗口保存这件事的身份、当前状态、参与者、原始资料、历史及待处理动作。App Card 是它在当前时刻呈现的一部分，随事件和用户决定更新。邮件、消息、日历、订单、物流和支付记录都可以成为同一事务的来源或操作目标。

例如，冰箱的送货预约已经完成后，窗口仍保留型号、发票和保修资料。将来收到维修报价时，同一个窗口再次出现需要用户决定的卡片。

建议区分三类生命周期：

| 类型 | 例子 | 生命周期 |
| --- | --- | --- |
| 长期对象 | 冰箱、汽车、住房 | 长期保留；购买、维修、续保等事件成为子事务 |
| 阶段性事件 | 年度体检、一次聚会、一次旅行 | 有阶段与完成条件；结束后可归档、检索、重新打开 |
| 持续计划 | 健身计划、孩子的兴趣班 | 周期性产生安排、反馈和调整；支持暂停及结束 |

这些类型可以组合：孩子的兴趣班是持续计划，一次演出或续费可以成为其中的阶段性事件。

## 研究证据

| 研究或标准 | 已有依据 | 对 OctoSense 的启发与证据边界 |
| --- | --- | --- |
| [Activity-Centric Computing Systems，CACM 2019](https://www.bardram.net/activity-centric-computing-systems/) | 系统综述覆盖 101 篇同行评审论文、68 种技术；核心是围绕现实活动整合设备、人员、服务和资源 | 为“事务作为窗口的组织单位”提供直接研究谱系；综述数量本身不能证明某一种 UI 有效 |
| [PARC TaskMaster，2003](https://hci.stanford.edu/seminar/abstracts/02-03/030214-bellotti.html) | 把任务管理嵌入邮件客户端；使用真实工作邮件进行了两周评估，部分用户之后继续使用 | 支持从处理邮件转向处理邮件承载的事务；属于受评估原型，并非成熟的通用 Agent 桌面 |
| [LookOut / Principles of Mixed-Initiative User Interfaces，CHI 1999](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/11/chi99horvitz.pdf) | 从邮件推断日程信息，协助填入日历；讨论不确定性、打断成本以及用户修改和控制 | 与“老师邮件引出日历动作”直接相关；理解内容、提出动作和实际提交应有清晰边界 |
| [OMG CMMN / Adaptive Case Management](https://www.omg.org/cmmn/index.htm) | 围绕持续变化的信息、关系和 case file 建模；事件可以使新的活动出现，活动顺序不必预先固定 | 适合订单售后、体检、家庭事务的动态分支；这是建模标准，不能当作消费者 UX 实验结论 |
| [Poppins / Just-In-Time Objectives，CHI 2026](https://doi.org/10.1145/3772318.3790713) | 根据用户当前上下文推断目标并生成交互工具；论文包含 17 人、每人约一小时的个人写作任务研究，另有上下文与输出评估 | 提供“根据当前目标生成可操作界面”的实验依据；尚未验证多周生活事务、跨服务执行或持久桌面窗口 |

这些材料共同支持研究方向，但没有在本次检索中找到足以证明完整 OctoSense 方案已经获得长期、跨领域用户验证的证据。也不能据此声称该组合具有首创性。

## 已部署系统与较新的实现方向

| 系统 | 官方资料支持的能力 | 与设想的距离 |
| --- | --- | --- |
| [TripIt](https://www.tripit.com/en-uk/web/how-it-works) | 将转发来的航班、酒店、租车等预订自动归入一次旅行的行程 | 旅行成为信息容器，是事务组织方式的产品先例；主要覆盖旅行领域 |
| [Shop：物流跟踪](https://help.shop.app/en/shop/delivery-tracking) | 从关联邮箱或 Shop Pay 购买记录加入订单，持续呈现配送状态，也支持手动添加 | 将邮件信息转为持续订单对象；官方说明履约仍由商家及承运商负责 |
| [Outlook Actionable Messages](https://learn.microsoft.com/en-us/outlook/actionable-messages/) | 邮件内直接批准、拒绝等；操作后卡片更新结果和剩余可用动作 | 原位行动与状态更新已经落地；卡片通常由服务方提供，容器仍是邮件 |
| [SAP Task Center](https://help.sap.com/docs/TASK_CENTER/08cbda59b4954e93abb2ec85f1db399d/9693186f1fe54cbe801085d6bdfe8287.html) | 集中来自连接系统的任务，在统一入口处理 | 跨系统任务入口已有产品实现；其主要单位是企业任务，完整个人生活事务仍需另行设计 |
| [Apple Notifications](https://developer.apple.com/design/human-interface-guidelines/notifications/) 与 [Live Activities](https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities) | 在系统表面呈现通知动作及持续活动，提供紧凑和展开形式 | 为桌面卡片的曝光、操作和展开提供先例；通知及活动仍由各应用发布，不等于统一事务模型 |
| [Microsoft Planner Agent](https://techcommunity.microsoft.com/blog/plannerblog/planner-agent-brings-work-management-directly-into-microsoft-365-copilot/4511720) | 从邮件、聊天等生成任务建议，用户在预览卡片修改并确认后写入 Planner；可在交互卡片更新任务 | 接近 LLM → 动作建议 → 确认 → 服务执行；所查官方发布材料标注 Frontier，属于预览证据，且主要承载于 Copilot 对话 |

“已部署”在这里指官方提供了相应产品能力，不能推导出其效果已经由独立研究或长期使用数据证明。

两项基础设施值得参考：

- [MCP Apps](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/) 允许工具返回表单、可视化及多步操作界面，官方机制使用宿主中的沙箱 HTML iframe。它能承载交互，但不会自动提供 OctoSense 的事务归并、生命周期或 Makepad 原生组件。
- [A2UI](https://a2ui.org/) 使用声明式界面描述交给宿主渲染。[官方渲染器列表](https://a2ui.org/renderers/)包含多种 Web 和移动框架；Makepad 若采用这一协议，需要对应的渲染适配。协议可用性与完整产品 UX 的有效性是不同问题。

## 适合的事务及窗口内容

以下是建议体验，尚未实现外部服务操作。

| 事务窗口 | 需要用户处理的卡片 | 原位展开的上下文 | 可关联的数据 |
| --- | --- | --- | --- |
| 你的冰箱 | 选择送货时段、确认上门安排、审阅维修报价、申请售后 | 订单、型号尺寸、发票、保修条款、商家和师傅对话、历史维修 | 订单邮件、商家接口、承运商、日历、维修服务 |
| 年度体检 | 选择预约时段、确认机构提供的项目、补交资料、安排报告咨询 | 预约及改期记录、机构原始须知、项目说明、原始报告和沟通记录 | 邮件、机构接口、日历、用户授权的健康记录 |
| 同学聚会 | 确认参加、选择日期、确认凑份子金额、修改人数 | 群聊原文、投票、地点方案、预算、收款及退款记录 | Messaging、日历、地图、支付服务 |
| 孩子的兴趣班 | 确认调课、申请请假、确认续费、填写活动回执 | 老师原话、整学期课表、剩余课时、缴费记录、历史通知 | 邮件、群聊、课程平台、家庭日历 |
| 你的健身计划 | 调整本周安排、选择替代训练、确认教练预约、记录完成情况 | 用户目标、计划版本、训练日志、教练反馈、用户授权的活动数据 | 日历、运动记录、教练消息、天气 |
| 一次旅行 | 接受改签方案、调整接驳、确认酒店安排、补充出行资料 | 完整行程、各项预订、改签规则、同行人消息、票据 | 邮件、航旅和酒店服务、日历、地图、天气 |
| 一次退货或理赔 | 选择取件时段、提交证明、确认处理方案 | 原订单、照片、政策原文、客服对话、处理进度 | 商家、物流、保险服务、文件 |
| 家庭账单或订阅 | 确认续订、调整方案、提出账单异议 | 合同、账单原件、历史变化、服务商往来 | 邮件、服务商接口、支付记录 |
| 工作中的交付或审批 | 审阅修改、选择方案、批准请求、确认下一步 | 文档版本、讨论、相关决策、依赖事项 | 邮件、消息、协作平台、文件和审批系统 |

共同特点是存在可持续追踪的主体或目标，外部事件会推进状态，有可界定的决定，用户偶尔需要恢复完整上下文。

持续写作、编程、设计和长时间内容浏览仍需要足够大的操作空间。事务窗口可以在需要时展开编辑器、阅读器或其他工具；不能假设所有交互都适合缩成批准或拒绝。

## 推荐窗口结构

```text
事务桌面
  你的冰箱           等待送货 · 1 项待确认
  年度体检           预约待选 · 2 项待处理
  同学聚会           等待大家回复
  孩子的兴趣班       课表已更新 · 待查看
  健身计划           本周已完成 2 / 3 次

打开「你的冰箱」
  当前状态与下一步
  待处理卡片：送货时间选择
  后续事项：送达后确认验收
  动态记录：已下单 → 已出库 → 等待送货
  资料：订单 / 发票 / 保修 / 原始往来
```

“家庭、健康、消费”适合作为筛选或空间分组。“待我决定、Agent 处理中、等待对方、已完成”适合作为状态视图。用户也可以从跨事务的“待我处理”入口依次处理卡片，但这里引用的应是原事务中的同一项动作。

### 同一张卡片的三种展开程度

1. **概览**：发生了什么、与我有什么关系、现在是否需要决定。
2. **处理**：原位展开时段选择、项目选择、回复编辑或其他必要控件；明确此次操作影响。
3. **上下文**：进一步展开原始邮件、真实对话 thread、文档及事件时间线；收起后保留表单输入和阅读位置。

Agent 摘要与原始资料应有明确区分。用户寻找事情来龙去脉时，需要能够检查原文以及后来的修改，不能只看到模型重新叙述的内容。来自不同来源的对话可以关联，但必须保留各自的作者、时间和来源。

### 动作完成之后

- 请求提交后，先显示处理中；收到服务端结果后更新为成功、失败或等待。
- 一张卡片完成后保留简短回执，窗口继续存在；“下一项”可以让用户继续处理。
- 外部信息晚到时，在原事务上更新；用户正在选择或编辑的内容不能因自动排序而跳走。
- “已阅”“确认收到”与实际提交预约、发送回复、支付有不同含义，按钮应表达真实动作。
- 已授权的调课可以显示“日历已更新”，提供查看和受支持的撤销；费用支付作为独立决定呈现。
- 关闭窗口、归档事务、忽略提示、取消预约应是不同操作；跨服务撤销需要对应服务支持，不能用本地返回代替。

## 对当前 image-to-appcard-flow 的影响

现有多个场景可以保留，但后续组织单位建议从固定演示步骤提升为持久事务：

1. 保留已经设计的原生卡片、控件和视觉规范，作为可组合的界面资源。
2. 为每个事务保存独立身份、来源关联、状态与动作记录。
3. 根据真实事件和用户决定选择或更新卡片；允许等待、改期、拒绝、失败恢复及重新打开。
4. 增加可原位展开的源文阅读器和事件历史。
5. 让桌面 tile、待处理队列和展开窗口共享同一动作状态，避免重复执行。

设计时一次生成 8–12 个 UX 界面仍可帮助保持一致，但运行时不应假定用户必须按图片顺序完成。实际事件可以改变下一步，也可能使已经结束的事务重新出现。

## 尚需验证的关键假设

- 用户是否自然地记住“某件事”的窗口，以及是否找得到暂停已久的事务。
- Agent 能否正确合并跨渠道信息，同时避免把两次体检或两台设备误并。
- 是否能区分新建议、既有决定、已取消安排和真正需要用户行动的信息。
- 摘要是否足够支持低成本决定，原位原文是否足够支持有疑问时的检查。
- 卡片是否减少切换和恢复上下文的成本，同时避免增加通知负担。
- 授权、执行、失败恢复与跨视图状态是否保持一致。

建议用现有体检、聚会、兴趣班场景，加上一个长期冰箱场景做探索性用户测试。比较传统应用流程、统一卡片队列和事务窗口，观察任务完成率、遗漏或误操作、恢复中断所需时间、原文查找及长期找回能力。多日测试才能发现一次演示无法呈现的归档、重开、消息迟到和任务积压问题。
